01

Reading an AIS/NMEA Exchange

AIS and NMEA 0183 are the vocabulary of shipboard navigation data — and, as Lesson 5 covers, neither carries built-in sender authentication. This lab has learners read a captured exchange field-by-field until the protocol stops feeling like noise.

Pairs with

Lesson 5 — Maritime & Industrial Communication Protocols

Tool

AIS / NMEA Message Analyzer (sim02.html)

Objective

Given a short, synthetic capture of NMEA 0183 and AIS traffic, correctly identify the sentence/message type, extract the key fields (position, course, speed, vessel identifier), and identify one field an attacker could alter without detection by the protocol itself.

Steps

  1. 1

    Load the capture into the AIS/NMEA Message Analyzer and identify the sentence type of the first message before decoding any fields.

  2. 2

    Decode the position and identity fields — latitude/longitude, MMSI, course, and speed — using the analyzer's field breakdown.

  3. 3

    Step through the remaining messages in the capture, noting anything that looks internally inconsistent (a speed that doesn't match two consecutive positions, for example).

  4. 4

    Identify the authentication gap: name one field in the message that a transmitter could set to any value with no protocol-level check catching it.

Deliverable: a short lab report (see the Lab Report Template) documenting the decoded fields and the authentication gap identified in Step 4.

02

Tracing a Converged Vessel Network Path

Lesson 1 introduces convergence as a historical shift; this lab makes it concrete by having learners trace one specific path from a shore-facing connection down to a safety-critical shipboard system.

Pairs with

Lesson 1 (convergence) and Lesson 4 (IT protocols inside shipboard networks)

Reference material

IT Protocols Inside Shipboard & Port Networks (lesson04.html)

Objective

Given a fictional vessel's network diagram (VSAT terminal, crew Wi-Fi, business network, and OT network including ECDIS and ballast control), trace the shortest path from the VSAT terminal to the ballast control system, and identify every point along that path where a segmentation control could have stopped it.

Steps

  1. 1

    Review the provided diagram and label each network segment (business, OT, crew/guest) before tracing anything.

  2. 2

    Trace the path hop by hop from the VSAT terminal to the ballast control system, listing every device or boundary the path crosses.

  3. 3

    Mark each crossing point where a firewall, VLAN boundary, or jump host currently exists — and where one is conspicuously absent.

  4. 4

    Propose one segmentation change that would break the traced path without disrupting the vessel's legitimate use of that connectivity.

Deliverable: an annotated version of the traced path (as a written report, since this lab is diagram-based rather than simulator-based) plus the proposed segmentation change.

03

Building an Access Control Matrix

Lesson 10 covers the shared bridge-console problem and role-based access; this lab has learners build the artifact a real OT security engineer would actually produce to reason about who can touch what.

Pairs with

Lesson 10 — Access Control & Identity Management Afloat

Tool

Access Control Matrix Builder (sim05.html)

Objective

Given a fictional vessel's role list (master, chief engineer, second officer, shore-based OEM vendor) and system list (ECDIS, engine automation, ballast control, crew Wi-Fi admin console), build a complete access control matrix applying least-privilege reasoning to every role/system pair.

Steps

  1. 1

    List every role and system in the Access Control Matrix Builder before assigning any permissions.

  2. 2

    Assign the minimum necessary access for each role/system pair — none, read-only, operate, or administer — justifying any "administer" assignment specifically.

  3. 3

    Add the shore-based vendor role last, and apply time-boxed, logged remote access rather than standing credentials.

  4. 4

    Review the finished matrix for any role with broader access than its justification supports, and correct it.

Deliverable: the completed matrix, exported or captured from the simulator, with a short written justification for the vendor's access scope.

04

Correlating an Alarm-Log Timeline

Lesson 11 covers monitoring and detection gaps on a vessel LAN; this lab has learners do the correlation work a fleet SOC analyst would do when a GNSS anomaly and an equipment alarm show up close together in time.

Pairs with

Lesson 11 — Monitoring, Detection & Maritime OT Incident Response

Tools

Alarm Log Correlation Trainer (sim03.html) and GNSS Time Sync & Spoofing Simulator (sim04.html)

Objective

Given a synthetic alarm log spanning several shipboard systems and a GNSS time-sync anomaly from the spoofing simulator, correlate the two data sources on a shared timeline and identify the most plausible sequence of cause and effect.

Steps

  1. 1

    Run the GNSS Time Sync simulator first and note the timestamp of any detected anomaly.

  2. 2

    Load the same time window into the Alarm Log Correlation Trainer and identify every alarm that fired within a few minutes of the GNSS anomaly.

  3. 3

    Build a single timeline combining both sources, ordered by timestamp, noting which alarms plausibly derive from the GNSS event and which are likely unrelated.

  4. 4

    State a hypothesis for what happened, and one additional data source that would help confirm or rule it out.

Deliverable: the combined timeline and the written hypothesis from Step 4.

05

Walking a Maritime OT Incident from Alert to Recovery

This synthesis lab pulls the threat landscape content from Lesson 6 and the incident response process from Lesson 11 into a single, end-to-end exercise — the closest this course gets to a live-fire drill while staying entirely within simulation and case-study analysis.

Pairs with

Lesson 6 (threat landscape) and Lesson 11 (incident response)

Format

Synthesis exercise — draws on the outputs of Labs 1–4 rather than a single dedicated simulator

Objective

Given a scripted, synthetic scenario (a described GPS/AIS anomaly detected mid-voyage, three days from the nearest port), walk the full incident lifecycle — detection, triage, containment, recovery, and after-action review — and produce the decisions a fleet SOC analyst and the vessel's crew would actually need to make at each stage.

Steps

  1. 1

    Detection: using the scenario's provided alarm and GNSS data (the same pattern as Lab 4), determine what triggered the alert and how confident the initial detection is.

  2. 2

    Triage: assess severity and scope — which systems are plausibly affected, and does this require containment now or continued observation?

  3. 3

    Containment: given that the vessel cannot simply be taken offline mid-voyage, decide what can realistically be isolated or fallback-switched (e.g., reverting to a secondary positioning source) without compromising safety of navigation.

  4. 4

    Recovery: describe what "back to normal operations" looks like, and what must be verified before trusting the affected system again.

  5. 5

    After-action review: identify one detection gap and one process gap the incident exposed, and one countermeasure from Lesson 7 that would close it.

Deliverable: a written incident walkthrough covering all five stages, submitted using the Lab Report Template.
